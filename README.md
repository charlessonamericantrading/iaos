# AgentOS

[![kernel-ci](https://github.com/charlessonamericantrading/iaos/actions/workflows/kernel-ci.yml/badge.svg)](https://github.com/charlessonamericantrading/iaos/actions/workflows/kernel-ci.yml)

An "AI-native" operating system project, explored in two independent, **not yet integrated** directions:

1. **[`agentos-kernel/`](agentos-kernel/)** — a real bare-metal kernel written in Rust (`#![no_std]`), booting on actual x86_64 hardware/QEMU. This is the actively developed half of the project.
2. **[`src/`](src/) + [`public/`](public/)** — a TypeScript/Express dashboard that simulates what an AI-agent OS's control plane might look like (scheduler, memory, sandbox). It is a UI mock: no real model calls, no persistence, everything in-memory. Parked in favor of the kernel.

There is no bridge between the two yet — `src/bridge.ts` only POSTs one canned sample event to demonstrate the shape of an API, it does not talk to the kernel.

## Current status (honest version)

The kernel **boots for real** in QEMU via the [`bootloader`](https://github.com/rust-osdev/bootloader) crate and reaches an interactive prompt. What's actually real hardware/software vs. simulated scaffolding, as of this commit:

Still entirely a ring-0 operation: nothing runs in ring-3 yet to prove this bit makes an actual difference - that remains the single biggest remaining step in this arc. Verified identical across 3 repeated boots, zero regression anywhere in the rest of the self-test suite. **`ring3.rs` (Fase 71) is that remaining step: the first genuine ring-0 -> ring-3 privilege-lowering transition this kernel has ever performed, completing the arc's core goal.** A real `iretq` stack frame is built by hand (`SS`/`RSP`/`RFLAGS`/`CS`/`RIP` pushed in the exact order `iretq` expects, `CS`/`SS` using Fase 68's own `user_code_selector`/`user_data_selector`, `RIP`/`RSP` pointing into Fase 70's own user-accessible page) and executed - and the "ring-3 program" waiting there is deliberately just one byte: `cli` (`0xFA`). `cli`/`sti` require `CPL <= IOPL` (IOPL defaults to 0), so executing it at `CPL=3` - which reaching and fetching it at all already requires - triggers a real `#GP`, caught by the EXISTING, unmodified GPF handler from this kernel's own original exception-handling work. Worked correctly on the very first attempt: the fault's own `InterruptStackFrame` dump shows `instruction_pointer` at exactly the user page's own address and, most conclusively, `code_segment: SegmentSelector { index: 5, rpl: Ring3 }` / `stack_segment: SegmentSelector { index: 4, rpl: Ring3 }` - the CPU's own reported privilege level at fault time, directly confirming genuine ring-3 execution, not inferred or assumed. Identical across 3 repeated local verification boots. **Deliberately exposed only as a new `ring3test` shell command, never invoked automatically at boot**: since this test intentionally ends in a permanent halt, baking it into the unconditional boot sequence would either remove the interactive shell from every real boot (if run before the prompt) or prevent this kernel's own later self-tests from ever completing (if run after) - a real, structural tension between "prove a deliberately destructive command works" and "keep the normal boot healthy," not an oversight. Consequently NOT part of the shared, automated CI boot-test assertions either (documented as such directly in `kernel-ci.yml`) - verified instead via a real, repeatable local test (temporarily invoked, removed before committing) exactly as described above. **Fase 72 completes the arc's remaining gap from Fase 69's own notes: the DPL=3 gate now reads REAL caller registers and dispatches to the REAL `syscall::dispatch_syscall`, instead of just incrementing a counter.** `extern "x86-interrupt"` handlers - what every other IDT entry in this kernel uses - are compiler-generated wrappers that only ever expose the pushed `InterruptStackFrame`, never the general-purpose registers (`RAX`/`RDI`/`RSI`/`RDX`) a real syscall convention uses to carry the call number and arguments. Vector `0x80` is now instead registered via `Entry::set_handler_addr` pointing directly at a hand-written `#[unsafe(naked)]` entry stub (`syscall_entry_asm`) - no compiler-generated prologue/epilogue at all, the same category of risk as `context_switch.rs`'s own asm, worked through with the same care: all 15 general-purpose registers are saved (deliberately more conservative than the real Linux/SysV convention, which only guarantees callee-saved registers survive), the real `RAX`/`RDI`/`RSI`/`RDX` are loaded into the SysV calling convention's own argument registers to call a normal Rust dispatch function, its `u64` return value is written back into the saved-`RAX` slot, every register is restored, and a real `iretq` resumes the caller. The exact push/pop offsets and the resulting stack alignment across the `call` boundary (interrupt frame + 15 pushes = 160 bytes, an exact multiple of 16, satisfying the SysV ABI's alignment requirement) were computed and verified by hand before writing any code, not assumed. Proven two ways: the existing ring-0 self-test (Fase 69's own) now pins real arguments (`SYS_SERIAL_PRINT`, `0`, `0`, `0`) instead of leftover register garbage and checks the real returned value (`dispatch_ret=0`); and a new, genuinely ring-3-originated test (`ring3.rs`'s `run_ring3_syscall_test`, the `ring3syscall` shell command) writes a real three-instruction "program" (`mov eax, 1` / `int 0x80` / `cli`) into Fase 70's user page and executes it from ring-3 - the resulting fault's `instruction_pointer` lands exactly at byte offset 7 (right after the 5-byte `mov` and 2-byte `int 0x80`), direct proof execution genuinely RESUMED in ring-3 after a real syscall round trip, not just that ring-3 could be entered once. Byte-for-byte identical across 3 repeated local verification boots (same discipline, and the same "ends in a permanent halt by design" reasoning, as `ring3test` above - also deliberately not CI-automated, for the identical reason). What remained open after Fase 72: a safe way to return from ring-3 to ring-0 *without* ending in a deliberate fault. **Fase 73 closes exactly that gap - the first ring-3 test in this whole arc that does NOT end in a permanent halt.** `enter_ring3` (a second hand-written `#[unsafe(naked)]` function) adapts `context_switch.rs`'s own `switch_to` trick across a ring-3 boundary: it saves the same 6 callee-saved registers (`rbp`/`rbx`/`r12`-`r15`) `switch_to` already established, in the same order, stores the resulting RSP into a static, then builds and executes a real `iretq` frame exactly like Fase 71's own test. The new piece is the return direction: a SECOND, dedicated DPL=3 interrupt vector (`0x81`, deliberately separate from the syscall vector rather than a special syscall number - simpler to reason about than one handler that sometimes resumes ring-3 and sometimes doesn't) whose handler discards the ring-3 context entirely, switches RSP to the stack `enter_ring3` saved, pops the same 6 registers, and returns - landing back in `enter_ring3`'s own ORIGINAL caller with a real value, as if it had returned normally. Two things make this safe rather than merely convenient, both confirmed rather than assumed: every IDT entry in this kernel defaults to a 64-bit INTERRUPT gate (confirmed via the `x86_64` crate's own `EntryOptions::minimal()`), which unconditionally clears `RFLAGS.IF` on entry, so a timer tick can never fire mid-transition and corrupt the shared `RSP0` stack; and `RSP0` (the TSS's dedicated ring3-entry stack), the kernel's own ordinary stack, and the ring-3 program's own stack (Fase 70's user page) are three genuinely distinct stacks that never overlap. Hit one real, instructive build error along the way: the naked stubs' direct `[symbol]` memory operands linked with `relocation R_X86_64_32S cannot be used against local symbol` - this kernel builds as a position-independent executable (`-pie`), which forbids absolute 32-bit addressing; fixed by making the RIP-relative addressing explicit (`[rip + {symbol}]`), the standard fix for exactly this class of PIE/PIC error. Verified with a real three-syscall ring-3 program (`mov eax,1`/`int 0x80`/`mov eax,42`/`int 0x81`, with a trailing `cli` as a safety-net fault detector that only ever executes if the exit path somehow failed to redirect): `exit_code=42` matched exactly on the very first attempt, and - the real proof this isn't just "entering ring-3 worked again" - the very next self-test in the boot sequence (`FRAME ALLOC`) fired immediately afterward, direct evidence the kernel's own execution genuinely continued rather than halting. Because this test doesn't end in a halt, it's the first ring-3 test that runs unconditionally as part of every normal boot and carries a normal CI assertion, no opt-in shell command needed. Byte-for-byte identical across 3 repeated boots. What remains open now: this only proves a ring-3 program can voluntarily exit ONCE with a scalar value - a real user/kernel pointer-validation boundary (for syscall arguments like `SYS_TENSOR_EVAL`'s) is still entirely absent, and nothing yet lets the kernel run MULTIPLE ring-3 programs or schedule between ring-3 and ring-0 work the way the existing cooperative/preemptive schedulers do for kernel-only tasks. |

| **Preemptive scheduler (real)** | Real, and now **PCB-unified too**. `scheduler/preemptive.rs` hooks the same `switch_to` primitive into the timer IRQ (`interrupts.rs`) so tasks that *never* call `yield_now` at all still get forced off the CPU - proven with two infinite, non-cooperating loops that both end up with large, nonzero counters after a timed window, which is only possible if the timer genuinely reclaimed the CPU from each without asking. Every format detail was checked against the real RFCs rather than relied on from memory, given how a wrong checksum fails silently: the receiving side just never replies, with no crash or error to point at the cause - a harder symptom to root-cause than the e1000 driver's own DD-bit mystery above. Pure byte-buffer logic, no hardware dependency at all - genuinely sending/receiving one over the wire needs a destination MAC address (ARP resolution, which doesn't exist yet) and would touch the e1000 TX/RX paths that are now proven correct and CI-asserted across three Fases; proving these primitives correct in isolation first, before anything depends on them, follows the same order the frame allocator and VFAT entry-building both used. **A real bug surfaced and got fixed during this Fase's own verification, not by chance**: the checksum-verification check initially compared a re-summed, already-checksummed buffer against `0xFFFF` - correct per RFC 1071's own wording, but only when read as "the sum *before* the final one's-complement step". This code's `internet_checksum` function returns that complement directly (`!sum`, the value meant to be *embedded* in a checksum field), so re-running it over a validly-checksummed buffer actually returns `!0xFFFF = 0x0000`, not `0xFFFF` - every genuinely valid buffer was being silently rejected. A pure round-trip test (build a message, then check it with the same function) would never have caught this, since both sides would have agreed with each other while disagreeing with any real peer computing the checksum independently - it was only caught because the self-test also included two independent, hand-computed checksum vectors verified by manual arithmetic before ever running the code. Fixed with a dedicated `checksum_is_valid` helper that encapsulates the correct constant in one place, rather than leaving every call site to compare against the right value itself. Verified: the two hand-computed vectors (one exercising the even-length case, one the odd-byte-padding case) match by hand; a full request/reply built via `build_icmp_echo` (odd-length end to end, so the integration path exercises the same padding logic too) round-trips through `parse_icmp_echo` correctly; a deliberately corrupted reply (one payload byte XOR-flipped) is correctly rejected; and a freshly-built IPv4 header's own checksum verifies too - all six checks passing identically across 3 repeated boots, zero regression across the entire prior self-test suite in the same boot log. |
| Syscall dispatcher | Still minimal, but one real number now genuinely does something beyond a stub. **`SYS_TENSOR_EVAL` (Fase 55) had been defined since before this session even started, but `dispatch_syscall` never had a match arm for it at all - calling it always fell through to "Unknown System Call Number", a genuine dead constant, the same class of gap Fase 50 found in `GgufTensorInfo`'s own long-parsed-but-unused `gtype` field.** Now wires to a real `TensorEngine::matmul_layer` call: a new `TensorEvalArgs` struct (weights/inputs/bias/outputs pointers+lengths, plus the two dimensions) is passed as a single pointer via `arg1`, since a real forward-pass layer needs more real parameters than 3 scalar syscall args could ever encode - the same reason real syscall ABIs commonly pass a request-struct pointer once a call outgrows a couple of plain numbers. Deliberately scoped as a small, ring-0-only slice of "make syscalls real", distinct from the much larger, still-deferred undertaking of an actual ring-3/ring-0 transition (this kernel has no user-mode GDT segments, no `RSP0` configured, and no `SYSCALL`/`SYSRET` or `DPL=3` interrupt gate at all - confirmed by directly reading `gdt.rs` before deferring that larger piece three Fases running). Verified with a small, fully hand-computable 2×2 layer (`weights=[1,2,3,4]`, `inputs=[1,1]`, `bias=[1,-10]`) that deliberately exercises ReLU's clipping branch too, not just addition: row 0 = `ReLU(1·1+2·1+1)=4.0`, row 1 = `ReLU(3·1+4·1-10)=ReLU(-3)=0.0` - both `syscall_ok` (the dispatcher returned its real success code, not the `u64::MAX` "unknown syscall" fallback it always had before) and `tensor_eval_correct` (the actual computed outputs match these hand-computed values exactly) passed on the very first boot, identically across 3 repeated boots, zero regression across the entire prior self-test suite. |

Nothing above is faked to look more finished than it is — this table is meant to stay accurate as the project grows, not to be a wishlist.

## Building & running the kernel

Requires the **nightly** Rust toolchain (pinned per-directory via `rust-toolchain.toml`) and [QEMU](https://www.qemu.org/).

```bash
# 1. Build the kernel itself
cd agentos-kernel
cargo build --release

# 2. Package it into a bootable disk image (separate crate, host target)
cd ../kernel-runner
cargo build --release
./target/release/kernel-runner "../agentos-kernel/target/x86_64-unknown-none/release/agentos-kernel" "../agentos-kernel/target/disk-image"

# 3. Boot it
qemu-system-x86_64 -drive format=raw,file=../agentos-kernel/target/disk-image/agentos-bios.img
```

Or just run [`agentos-kernel/boot_kernel.bat`](agentos-kernel/boot_kernel.bat), which automates all three steps and opens an interactive QEMU window.

For a headless run with serial output captured to your terminal instead:

```bash
qemu-system-x86_64 -drive format=raw,file=agentos-kernel/target/disk-image/agentos-bios.img -serial stdio -display none -no-reboot -no-shutdown
```

## Running the TypeScript dashboard simulator

```bash
npm install
npm run build
npm start
```

Serves the mocked dashboard UI in `public/` against the in-memory "kernel" in `src/server/kernel.ts`. Nothing here talks to real hardware or a real model.
