# AgentOS

[![kernel-ci](https://github.com/charlessonamericantrading/iaos/actions/workflows/kernel-ci.yml/badge.svg)](https://github.com/charlessonamericantrading/iaos/actions/workflows/kernel-ci.yml)

An "AI-native" operating system project, explored in two independent, **not yet integrated** directions:

1. **[`agentos-kernel/`](agentos-kernel/)** — a real bare-metal kernel written in Rust (`#![no_std]`), booting on actual x86_64 hardware/QEMU. This is the actively developed half of the project.
2. **[`src/`](src/) + [`public/`](public/)** — a TypeScript/Express dashboard that simulates what an AI-agent OS's control plane might look like (scheduler, memory, sandbox). It is a UI mock: no real model calls, no persistence, everything in-memory. Parked in favor of the kernel.

There is no bridge between the two yet — `src/bridge.ts` only POSTs one canned sample event to demonstrate the shape of an API, it does not talk to the kernel.

## Current status (honest version)

The kernel **boots for real** in QEMU via the [`bootloader`](https://github.com/rust-osdev/bootloader) crate and reaches an interactive prompt. What's actually real hardware/software vs. simulated scaffolding, as of this commit:

| Subsystem | Status |
|---|---|
| Boot (`bootloader` crate, BIOS) | **Real.** Verified boot to `AgentOS>` prompt. |
| GDT / IDT / CPU exceptions | **Real.** breakpoint, double-fault (own IST stack), page-fault, GPF, divide-error, invalid-opcode all wired and verified via a live `int3` self-test. |
| 8259 PIC + hardware interrupts | **Real.** PIC remapped to vectors 32-47 (avoids colliding with CPU exception vectors 8-15), interrupts enabled, timer (IRQ0) and keyboard (IRQ1) are interrupt-driven, not polled. |
| Physical memory / paging / heap | **Real.** Frame allocator walks the actual `BootInfo` memory map (skips regions already used by the kernel/bootloader); the heap is properly mapped page-by-page before use. `alloc` (`Vec`, `Box`, `String`) works. 1 MiB heap (raised from an initial 100 KiB after `cat`-ing a real file proved that too small - see FAT12 row below). The same frame allocator instance is now also reachable *after* boot's initial heap setup via a global `memory::frame_allocator::allocate_frame()` - a prerequisite for any future code needing dedicated physical memory outside the heap (a real e1000 TX/RX descriptor ring being the motivating case - see NIC row below). Deliberately the *same* allocator, not a fresh one built later from the same memory map: a fresh one would start handing out frame 0 again, which the heap already owns by then. Verified by allocating 3 frames after boot and write/read-back-testing a pattern through each (via the same `PHYS_MEM_OFFSET` mechanism the VGA buffer and e1000 probe use) - came back distinct and exactly 4 KiB apart (`0x163000`, `0x164000`, `0x165000` locally), proving these are genuine, usable, non-overlapping memory, not just plausible numbers. |
| Agent scheduler (`ps`-visible) | **Now really unified with both the cooperative and preemptive schedulers** (next two rows): `spawn_cooperative` and `run_preemptive_demo` both register real PCB entries via `SCHEDULER.lock().spawn(...)`, and each scheduler keeps its entries' `state`/`stack_pointer` honest as tasks actually run, yield/get switched, and finish - `ps` genuinely reflects live scheduler state now, not just a fixed table. Still partial for one thing: the 4 processes spawned directly at boot as a self-test (`kernel-supervisord` etc.) have PCB entries but no real stack/registers behind them - nothing ever actually schedules them as tasks. |
| Cooperative task scheduler | Real, and now **PCB-unified** (previous row). `scheduler/context_switch.rs`'s `#[unsafe(naked)]` `switch_to` swaps RSP + the 6 callee-saved registers between stacks (xv6-style) - `spawn_cooperative`/`yield_now`/`finish_current_task` build a priority-ordered N-task cooperative scheduler (up to 4 tasks) on top of it, and each task is now a real `ps`-visible process, not just an internal one. Verified two ways in QEMU: `ps` dispatched from *inside* a running task shows it `RUNNING` with a real (nonzero, heap-range) stack pointer while its not-yet-scheduled siblings still show `READY` with no stack pointer recorded yet; `ps` again after the demo shows all three `DEAD` (terminated) with distinct real stack pointers exactly `TASK_STACK_SIZE` (16 KiB) apart, matching their actual heap layout - strong evidence these are genuine addresses, not placeholders. A task only ever changes on its own voluntary `yield_now` call. |
| **Preemptive scheduler (real)** | Real, and now **PCB-unified too**. `scheduler/preemptive.rs` hooks the same `switch_to` primitive into the timer IRQ (`interrupts.rs`) so tasks that *never* call `yield_now` at all still get forced off the CPU - proven with two infinite, non-cooperating loops that both end up with large, nonzero counters after a timed window, which is only possible if the timer genuinely reclaimed the CPU from each without asking. Two real, subtle bugs surfaced and got fixed getting here, both the same root cause: state shared between an interrupt handler and normal code needs `AtomicBool`/`AtomicU64`, not a plain `static mut` - in a release+LTO build, the compiler hoisted a `while flag { hlt() }` poll loop's read out entirely (an infinite hang, since it never noticed the interrupt handler had cleared the flag), and separately treated a counter only ever incremented inside an infinite loop with no in-function reader as having no provable side effect. Neither was caught by clippy or by reasoning about the design alone - only by actually booting it and getting a genuinely wrong/hung result, then diagnosing why. **PCB unification needed real interrupt-safety care**, unlike the cooperative case: `tick()` runs inside the timer interrupt handler, so it uses `SCHEDULER.try_lock()`, never the blocking `.lock()` - taking a normal lock there would deadlock permanently on this single core if the timer ever fired while normal code held it mid-update, since that code could never resume to release it until this very handler returns. A skipped update (vanishingly rare, and harmless - `ps` is diagnostic-only) self-corrects the next tick, ~55ms later. Verified the same two ways as the cooperative case, plus 3 repeated full boots to check for interrupt-timing-dependent flakiness specifically (none observed - identical serial output every run). |
| Context switch primitive (hand-written asm) | **Still flagged for human review** - not yet reviewed as of this note; built further on it anyway per the project owner's explicit instruction not to wait. Both schedulers above share it. |
| Interactive shell | Real (small). The `AgentOS>` prompt is IRQ1-driven (not polled), buffers a real line (heap-backed `String`) with backspace, Left/Right cursor movement, Shift (uppercase letters plus `~`/`-`/`_`), and Up/Down command history (a real `Vec<String>`), and dispatches `help` / `ps` / `mem` / `uptime` / `date` / `lspci` / `disk` / `ls` / `cat` / `touch` / `rm` / `mkdir` / `rmdir` / `clear` against the live scheduler, KV-cache, heap, timer-tick, real-time-clock, and real disk/filesystem state - not canned output. Insert/backspace both act at the cursor, not just at the end of the line - typing "hep", pressing Left once, then typing "l" correctly produces "help", not "hepl" or "lhep". Verified in QEMU: that exact sequence dispatches the real `help` command (its actual output appears in the log), not an "Unknown command" line. **Shift was a real, practical gap, not a nice-to-have**: before it, a real person at the keyboard could never actually type `cat KERNEL~1` themselves - no way to produce an uppercase letter or `~` at all - even though self-tests could dispatch it directly. Verified by feeding a realistic scancode sequence holding Left Shift across "KERNEL~" (letters plus the backtick key, which shifts to `~`) and releasing it before the unshifted "1": dispatches the real `cat` command a second time in the log (identical byte count to the direct self-test), not an "Unknown command". **`touch`/`rm` close a similar gap for file writes**: `Fat12Info::create_file`/`delete_file` (see the FAT12 rows below) existed for several Fases but were only ever reachable from hardcoded `main.rs` self-tests - a real person at the prompt had no way to create or delete a file themselves. `touch FILENAME [content...]` joins whatever's left on the line (single-spaced - this shell has no quoting, so exact original spacing isn't preserved) and creates a new file with it as content; `rm FILENAME` deletes one. Both are FAT12-only, matching `create_file`/`delete_file` themselves - a real FAT32 disk would get a clear "not implemented yet" error rather than a silent no-op, currently untested in practice since this disk is FAT12. Verified in QEMU through the *actual* `dispatch_command` parsing path (not by calling `Fat12Info` methods directly, unlike the tests that first proved `create_file`/`delete_file` themselves correct): `touch SHELLNEW.TXT hello from the real shell` creates a real 25-byte file, `cat` reads the exact same content back (first 4 bytes `68 65 6c 6c` - "hell", confirming genuine content, not just a matching length), `rm` deletes it, and a second `cat` then fails with "file not found" - identical across 3 repeated boots. |
| KV-cache memory manager | Real (small). Each block is a genuine heap allocation (`Box<[u8]>`, 4 KiB - sized for the current 1 MiB demo heap, not a realistic model-serving size yet); freeing a block really deallocates it. Previously used a fabricated address (`0x2000000 + idx*size`) that nothing was ever mapped to. |
| GGUF model loader / tensor engine | **The header, a real tensor-info entry, AND the tensor weight values it points to are now all real disk I/O, not compile-time constants - the tensor math itself is still an honest toy.** Built up over three Fases: first the 24-byte header round-tripped through a real file (`MODEL.BIN`) via `create_file`/`read_file`; then the same file grew 64 bytes of raw little-endian `f32` weight data, decoded back via a new `GgufModelLoader::decode_f32_le`. This Fase adds the piece both left out: a real `GgufTensorInfo::parse` between the header and the weight bytes - a length-prefixed name, two dimensions, a quantization type, and a byte **offset** to that tensor's own data elsewhere in the file - and the weight bytes are now located by *following that parsed offset*, not assumed to sit immediately after a fixed-size header. Deliberately still a simplified, honest slice of real GGUF, not a compliance claim: `u32` fields throughout instead of GGUF's `u64` (more range than this kernel's own toy tensors will ever need), exactly one tensor-info entry rather than a general `tensor_count` of them (the header's own declared count is set to `1` now specifically so it matches what's actually present - no longer a cosmetic unused number), and no KV-metadata section (`kv_count` honestly set to `0`, since none is written or parsed). Loading *real quantized* tensor formats (the actual point of GGUF as a format) remains separate, larger scope. Verified the full round trip (write, read back, byte-for-byte match, delete), that the parsed tensor-info entry's name/dimensions/type/offset all match what was written, that following the parsed offset and decoding *those* bytes reproduces the original weight values exactly (a lossless byte round trip, safe to assert bit-for-bit), and that running the matmul on those offset-located, disk-decoded weights produces the same known-correct output the original hardcoded array always did - all six checks passed identically across 3 repeated boots, zero regression across the entire FAT12/shell/VFAT self-test suite in the same boot log. |
| PCI bus enumeration | Real. `pci.rs` reads real config space via the legacy `CONFIG_ADDRESS`/`CONFIG_DATA` I/O ports (read-only - never reconfigures anything) and the `lspci` shell command lists what it finds. Verified against known-good hardware IDs, not just "didn't crash": QEMU's default machine reports exactly the expected i440FX host bridge (`8086:1237`), PIIX3/4 ISA/IDE/ACPI bridges (`8086:7000`/`7010`/`7113`), standard VGA (`1234:1111`), and an e1000 NIC (`8086:100e`) - all real, recognizable vendor:device IDs, not fabricated ones. Only scans bus 0 (no bridge recursion yet). |
| Real-time clock (CMOS RTC) | Real. `rtc.rs` reads the actual wall-clock date/time via the legacy CMOS I/O ports (0x70 index/0x71 data) - the `date` shell command shows it. Waits out the chip's Update-In-Progress flag first (a real, if uncommon, torn-read hazard if ignored) and checks Status Register B rather than assuming BCD vs. binary or 12h vs. 24h mode, since real hardware (and QEMU's emulation) can be configured either way. Verified about as concretely as a "real" check can be: QEMU syncs this clock to the host's actual wall-clock time by default, and the value read back during local testing matched the real date/time at the moment of the test, to the second. No century register exists reliably, so the year assumes 20xx. |
| Disk I/O (ATA PIO) | **Real, both read and write.** `ata.rs` reads/writes real 512-byte sectors on the primary ATA master via classic PIO (ports 0x1F0-0x1F7) - the `disk` shell command reads LBA 0 and checks for the `0x55AA` MBR boot signature, which is genuinely present since it's reading our own disk image. **Caught a real bug getting the read side working**: the drive raises IRQ14 on command completion regardless of whether anything is waiting on it, and this kernel had no handler for that vector at all - the first real read double-faulted the instant interrupts came back on after the operation. Fixed with a real (if minimal) `ata_primary_interrupt_handler` in `interrupts.rs`, not just by suppressing the symptom - and that same fix is why `write_sector` (added later, prerequisite for any future FAT write support) worked cleanly on the first real boot test, no repeat of that bug. `write_sector` follows the same PIO handshake as reads (select drive/LBA, wait for `DRQ`, transfer 256 words) plus a `CACHE FLUSH` (`0xE7`) afterward so a caller getting `Ok` back knows the write is genuinely committed, not just buffered. Verified with a real write-then-read-back test at a sector safely inside the FAT12 partition's unused tail, confirmed byte-for-byte identical across 3 repeated boots. |
| Partition table (MBR) | Real. `partition.rs` parses the 4 primary partition entries out of the boot sector already read via ATA. On our own disk image this finds two real bootable entries: a small internal region (the `bootloader` crate's own boot stages) and a partition typed `0x0C` ("FAT32 LBA") - **which turned out to actually be formatted FAT12**, see below. |
| FAT32 / FAT12 filesystem | **Real - read (`ls`/`cat`), overwrite-existing-file write, and now genuine new-file creation too, all verified end-to-end.** `fat32.rs` parses the BPB and can walk cluster chains / list a directory / read a file by name - **but our own disk's `0x0C`-typed partition is actually FAT12**, confirmed by reading the raw boot sector (`root_entry_count=512`, and the on-disk filesystem-type string literally reads `"FAT12   "`, volume label `"agentos-ker"`) - the `mbrman`/`fatfs` tooling that builds our disk image apparently doesn't always match the MBR type byte to the filesystem it actually formats for a volume this small. `shell.rs` tries FAT32 first and falls back to `fat12.rs` (packed 12-bit FAT entries, two per 3 bytes; fixed-location root directory instead of a cluster chain) when it doesn't apply - which is what makes both commands actually work on this disk. `ls` lists all 3 real files present (`BOOT-S~1`, `BOOT-S~2`, `KERNEL~1` - the `bootloader` crate's own two stages plus our kernel binary; each roughly 116-150 KiB, exact byte counts not pinned anywhere since they turned out to shift a little between build machines - see next paragraph). `cat KERNEL~1` reads the whole file back through a real cluster-chain walk (its length matching whatever `ls` reported that boot), and the first 4 bytes are always `7f 45 4c 46` - the genuine ELF magic number (`\x7fELF`), a build-independent invariant and about as strong a correctness proof as available without a full checksum. **Found the hard way (three times)**: first, the initial FAT32 code silently misread FAT12's differently-shaped BPB as FAT32 fields, computing a garbage LBA in the billions; fixed by checking `root_entry_count` (FAT32 always zeros it, FAT12/16 never do - the standard, authoritative discriminator) and failing with a clear, honest message instead of guessing. Second, actually `cat`-ing a real file panicked with a heap-allocation failure - every real file on this disk (116-148 KiB) turned out to be bigger than the entire 100 KiB heap that existed at the time, since `read_file` needs one contiguous allocation for the whole file; fixed by raising the heap to 1 MiB (see memory row above). Third, a CI regression check that hardcoded the exact byte count seen locally (`KERNEL~1 132992 bytes`) promptly failed on the Linux CI runner, which built a `KERNEL~1` of 132960 bytes from the identical source - the kernel ELF's own size isn't stable across build machines, so the CI check was rewritten to assert on the build-independent ELF magic bytes instead of a specific length. Directory-entry parsing (32-byte short-name entries, VFAT long-name entries recognized and skipped) is shared between both filesystem modules via `fat_common.rs`. **Fourth thing found the hard way**: `fat12::write_file` (new at the time - overwrote an existing file's content at the same byte length only, reusing its existing cluster chain with no directory/FAT changes; resizing came later, see the dedicated FAT12 file resize row below) was first tested by overwriting `BOOT-S~2` with a throwaway pattern, on the assumption that nothing in this kernel's own self-tests reads it so it was "safe." Wrong assumption, caught by a routine repeat-boot-test: `BOOT-S~1`/`BOOT-S~2` are the `bootloader` crate's own boot-stage *executables*, run by the BIOS before this kernel exists - QEMU's `-drive` writes straight through to the host `.img` file, so leaving that overwrite in place corrupted the boot chain for every subsequent boot against the same image (the first boot looked fine, since its own chain had already handed off to this kernel before the corruption happened; only the *next* boot attempt hit a totally empty serial log, no panic, because a corrupted stage 2 never got far enough to run any kernel code at all). Fixed by having the self-test unconditionally restore the original content afterward - confirmed safe across 3 repeated boots against the same unregenerated image. |
| FAT12 new-file creation | **Real - genuinely new files, not just overwriting existing ones - and now of any size, not just single-cluster.** `Fat12Info::create_file` finds as many free clusters as the data needs (`find_free_clusters`, one pass over the in-memory FAT collecting distinct `0x000` entries - calling a "find one free cluster" function repeatedly would just return the same cluster every time, since nothing marks one "taken" until its FAT entry is actually written) and a free root-directory slot (first byte `0x00`/`0xE5`), writes the data across all of them, chains each cluster to the next in the FAT (last one marked end-of-chain), and writes a real short-name (8.3) directory entry - including a genuine creation timestamp read from the CMOS RTC (Fase 20), not a zeroed placeholder. Short names only still (no VFAT long-name entries). Writing a 12-bit FAT entry correctly handles the one real edge case that format has: at specific cluster numbers (341, 682, 1023...) the packed entry straddles a 512-byte sector boundary, so both sectors are read/written when that happens rather than assumed never to occur. Verified in QEMU: creates `AGENTOS.TXT`, reads it back and confirms the content matches, and `ls` genuinely shows the entry count going from 3 to 4. Repeat boots against the same unregenerated image correctly detect the file already exists (no duplicate entry, no double-allocated cluster) and still read back the same real content - confirmed identical across 3 repeated boots, learning directly from the FAT12-write lesson above about what "safe to run every boot" actually requires. **Multi-cluster support (originally deferred - "several free-cluster lookups tracked against each other so the same free cluster is never handed out twice" was real, meaningfully more bookkeeping) verified separately**: creates a 3100-byte file (this disk's clusters are 1024 bytes each, so this genuinely needs 4 chained clusters, not 1), reads it back byte-for-byte against a deterministic pattern (not just a matching length), and deletes it - which also happens to be the first real test of `delete_file`'s cluster-chain walk against an actual multi-cluster chain (Fase 27 only ever proved that logic against single-cluster files, though it was written generally from the start). All correct, identical across 3 repeated boots. |
| FAT12 file deletion | **Real - frees both the cluster chain and the directory slot, not just a cosmetic marker.** `Fat12Info::delete_file` finds the entry's exact on-disk location (`find_entry_location`, which tracks slot index unlike `list_root_directory`), walks its full cluster chain zeroing each FAT entry back to `0x000`, and marks the directory entry's first byte `0xE5` (the standard FAT convention `find_free_root_entry` already knew to treat as reusable). **Found the hard way, a genuine cache-coherence bug**: the very first test run failed with `cluster chain hit a free (0) entry unexpectedly`, even though the file had been created moments earlier in that same boot. Root cause: `write_fat_entry_to_disk` (used by both `create_file` and `delete_file`) wrote the new FAT value straight to disk but never updated the in-memory `fat_bytes` copy loaded once at mount time - so any later call within the same `Fat12Info` that consulted the cache (`next_cluster`, `find_free_cluster`) saw stale, pre-write data. This had been silently latent since `create_file` was added: `read_file` never surfaced it because its read loop returns as soon as it has enough bytes, so a single-cluster file never reaches its own `next_cluster` call - `delete_file` is the first caller that walks the chain unconditionally, regardless of file size, which is exactly why it's the one that exposed a bug that had been sitting there since the previous Fase. Fixed by having `write_fat_entry_to_disk` write the same two bytes into `fat_bytes` right after the disk write succeeds, keeping the cache coherent for the rest of that mount's lifetime. Verified in QEMU: creates a dedicated `DELETEME.TXT` (kept separate from the already-verified `AGENTOS.TXT`), confirms it exists, deletes it, then confirms `read_file` now fails and `ls`'s entry count drops back down - correct across 3 repeated boots against the same unregenerated image, including boots where the file first had to be freshly re-created (since the previous boot's delete had already removed it from disk). |
| FAT12 file resize (grow + shrink) | **Real - `write_file` can now change a file's size, not just overwrite it at the same length.** Originally same-size-only ("resizing needs FAT chain growth/shrink... substantially more work, deliberately not attempted") - closed once multi-cluster `create_file` (previous row) had already built the one piece resizing needed too: safely allocating (or, for shrinking, freeing) several clusters at once. `write_file` now walks the file's existing chain, computes how many clusters the new data needs, extends the chain with `find_free_clusters` if growing or frees the excess trailing clusters if shrinking, writes the data across the (possibly resized) chain, and patches the directory entry's size field on disk - `start_cluster` never changes, since the first cluster of an existing file's chain never does. Verified in QEMU with a single dedicated file taken through all three states in one boot: created at 500 bytes, grown to 2500 (needing 3 clusters on this disk's 1024-byte clusters, i.e. genuinely allocating 2 *new* ones and extending the chain), then shrunk to 300 (freeing those same 2 clusters back to the FAT) - each phase checked byte-for-byte against a *different* deterministic pattern (different modulus, different length) specifically so a bug leaving stale bytes from an earlier phase in place would show up as a mismatch rather than an accidental false pass. All three phases correct, plus the file is deleted afterward to keep the test self-cleaning - identical across 3 repeated boots. The original same-size overwrite test (`BOOT-S~2`, previous section) still passes unchanged, confirming the generalization didn't regress the simplest case. |
| FAT12 subdirectories (create, list, delete, nested) | **Real - `mkdir` creates a genuine walkable subdirectory, `ls DIRNAME` lists it, `rmdir` deletes it.** Unlike the fixed-location root, a subdirectory is just an ordinary single cluster holding real `.` (points to itself) and `..` (points to its parent - cluster `0` is the real FAT convention meaning "the parent is the root", since the root has no cluster number of its own to point back to) entries, marked `ATTR_DIRECTORY` in its own root-directory entry. **A real correctness point, handled deliberately rather than assumed**: a newly-allocated cluster's FAT entry being `0x000` (free) says nothing about what's still sitting in its actual *data* bytes on disk - this kernel's own self-tests create-then-delete several files every single boot, so a fresh cluster can easily still hold a previous file's leftover content. That's harmless for a plain file (only bytes up to its logical size are ever read back), but a directory's bytes are always parsed as structured entries - stale data past `.`/`..` could be misread as bogus additional entries. `create_directory` explicitly zeroes every sector of the new cluster beyond the first, not just the one holding `.`/`..`. Verified in QEMU: `mkdir TESTDIR` then `ls` shows it in the root as a real directory (`dir=true`, a genuine cluster number), and `ls TESTDIR` shows **exactly 2 entries** - `.` (pointing back to its own cluster) and `..` (cluster `0`) - proving the zeroing worked, not just that the two real entries happen to also be present alongside undetected garbage. `TESTDIR` deliberately persists across repeat boots (like `AGENTOS.TXT` does) to keep exercising `mkdir`'s "already exists" tolerance path. `rmdir` (added once `mkdir`/`ls` were proven solid) frees the directory's cluster and marks its root entry deleted - the same mechanics `delete_file` already uses - and refuses to delete a non-empty directory (checked via its own `.`/`..`-only content), the standard safe `rmdir` semantic; verified with a separate, fully self-cleaning `mkdir`→`rmdir`→confirm-gone round-trip each boot. File I/O *inside* a subdirectory (not just root) is now real too - see the dedicated row below. **Directories can now nest one level deeper too**: `create_directory`/`delete_directory` were generalized the exact same low-risk way as the file-I/O row below - an internal `DirLocation` parent parameter, existing functions kept as unchanged-signature wrappers, new `create_directory_in`/`delete_directory_in` for a directory whose parent is itself a subdirectory rather than root. The one genuinely different piece for a nested directory: its `..` entry must point to the *parent's real cluster*, not always `0` - `0` is specifically the "parent is the root" convention, which no longer holds once a directory's parent is itself another directory. Verified in QEMU: creates an outer directory, creates an inner one nested inside it, confirms the outer directory's listing shows exactly 3 entries (`.`, `..`, and the inner directory - no stale garbage), and - the real correctness check - confirms the inner directory's `..` entry's cluster number **equals the outer directory's own cluster**, not `0`. All four checks (`outer_count_ok`/`dotdot_ok`/`delete_inner_ok`/`cleanup_ok`) correct on the first attempt, zero regression across all eight prior FAT12 self-test suites confirmed in the same boot log, correct across 3 repeated boots. Not yet exposed via shell path syntax (that needs multi-segment path parsing, e.g. `A/B/file.txt` - a separate concern) - proven at the `Fat12Info` API level first, same order as everything else in this arc. |
| FAT12 file I/O inside a subdirectory | **Real - `create_file`/`read_file`/`write_file`/`delete_file` can now target a subdirectory, not just the root.** Previously the single biggest remaining FAT12 gap, flagged as future work across several prior Fases. Closed with a deliberately low-risk, additive design rather than changing any existing function: a small internal `DirLocation` enum (`Root` or `Cluster(u32)`) plus private `*_impl` functions holding the real logic - the existing `create_file`/`read_file`/`write_file`/`delete_file` became thin, **signature-unchanged** wrappers calling their `_impl` with `DirLocation::Root`, and new `create_file_in`/`read_file_in`/`write_file_in`/`delete_file_in` functions (taking a directory's cluster number) call the same `_impl` with `DirLocation::Cluster(...)`. `find_entry_location`/`find_free_root_entry` were generalized the same way, via a new shared `directory_sectors` helper that flattens "which sectors make up this directory" (the root's fixed range, or a subdirectory's cluster chain walked to completion) into one list every entry-scanning function iterates identically either way. This needed **zero new low-level disk-I/O code** - multi-cluster allocation (`find_free_clusters`), resize (`write_file`'s grow/shrink), and cluster-chain listing (`list_directory`) already existed from earlier Fases and slotted in directly. Deliberately does **not** grow a subdirectory's cluster chain if it fills up (same single-cluster limitation `create_directory` already has). **Verified with real care for regressions**, since this touched four already-extensively-tested functions: the one exact error string CI already asserts (`"FAT12: file not found in root directory"`, from `cat`'s failure path) was deliberately preserved byte-for-byte for the root case (a `match`-selected message keeps the subdirectory case honestly distinct: `"...in directory"`). Verified in QEMU: creates a dedicated subdirectory, creates a file inside it, reads it back matching, grows it via `write_file_in` (1500 bytes, needing multiple clusters), reads that back matching too, deletes the file, confirms it's gone, then deletes the now-empty subdirectory itself - all four steps genuinely correct on the very first attempt. Every one of the five pre-existing FAT12 self-test suites (overwrite, create, delete, multi-cluster, resize) plus all shell-level tests (`touch`/`rm`/`cat`/`mkdir`/`rmdir`) confirmed passing identically, unchanged, in the same boot log - real, checked evidence of zero regression, not just an assumption from the additive design. Correct across 3 repeated boots. **`touch`/`cat`/`rm` now understand a `DIR/FILE.EXT` path too** (one level deep, matching what `Fat12Info` itself supports) - `shell.rs` splits it and resolves `DIR` to its cluster before calling the `_in` functions above, falling back to the existing plain-name/root behavior unchanged when there's no `/`. Verified through the real interactive `dispatch_command` parsing path (not calling `Fat12Info` directly): `touch PATHTEST/INSIDE.TXT hello via a real path` creates a real 21-byte file inside a fresh subdirectory, `cat` reads it back matching (first 4 bytes `68 65 6c 6c` - "hell"), `rm` deletes it, a second `cat` correctly fails with the subdirectory-specific "not found in directory" message (not the root one - proof the path genuinely routed to the right place), and `rmdir` removes the now-empty test directory - fully self-cleaning, identical across 3 repeated boots. |
| FAT12 subdirectory growth (multi-cluster directories) | **Real - a subdirectory can now grow past its first cluster once its entry slots run out**, instead of `create_file_in`/`create_directory_in` simply failing with "directory is full" the moment a subdirectory's one starting cluster (32 entries on this disk, 2 of which are always `.`/`..`) is exhausted. `find_free_entry_in` now falls back to `grow_directory` when no free slot exists in a subdirectory's current chain: walks to the chain's real tail, allocates and zeroes a fresh cluster (the same "stale bytes are dangerous for directories" zeroing `create_directory` already does), and chains it on - reusing the exact allocate-then-chain primitives `create_file`/`write_file` already use for a *file's* chain, since growing a directory's chain isn't fundamentally different, just applied to entries instead of file bytes. The root directory itself still can't grow (a real, permanent limit - its size is fixed by the BPB, not a cluster chain, so a full root is a genuine error, not a gap). **A real bug found by this Fase's own self-test, not by chance**: the first attempt correctly created all 31 test files and reported the right final entry count, but the *last* file's content failed to read back correctly and the test directory couldn't be deleted afterward - both symptoms of silent data corruption. Root cause: `create_file_impl`/`create_directory_impl` both picked a free cluster for their own new content *before* asking for a free directory-entry slot - but `find_free_clusters` only reads the in-memory FAT cache, it doesn't reserve anything until a later write actually commits it. When the entry-slot search subsequently triggered `grow_directory` (which *does* immediately commit its own new cluster), it could - and, once actually exercised at scale, did - pick the exact same "free" cluster the file/directory's own content had already been assigned moments earlier, since neither allocation had told the other about it yet. Fixed by reordering both functions: find (and, if needed, grow into) the entry slot *first*, so any directory growth is committed to the FAT before the new file/directory's own cluster search ever runs. Verified with a dedicated test creating 31 one-byte files inside a fresh subdirectory (this disk's exact per-cluster capacity, so the 31st genuinely requires a second cluster to exist at all) - all created, the directory listing showing exactly 33 entries (`.`, `..`, 31 files), the 31st file's content read back correctly (the single strongest proof the new cluster is genuinely functional storage, not just "created without erroring"), all 31 deleted, and the directory itself removed afterward - all five checks correct after the fix, identical across 3 repeated boots, with zero regression confirmed across all nine other FAT12 self-test suites in the same boot log. |
| FAT12 long file names (VFAT) | **Real - genuine long file names (spaces, mixed case, anything past what 8.3 allows, up to 195 characters), not just a display cosmetic.** `create_file`/`create_directory` fall back to generating a real VFAT sequence - one short-name alias entry plus as many long-name entries (attribute `0x0F`) as the name needs - whenever a name doesn't fit plain 8.3; the short-name checksum every long entry carries came straight from the Linux kernel's own `Documentation/filesystems/vfat.txt` rather than reimplemented from memory, given how easy that exact kind of bit-twiddling is to get subtly wrong. The read side (`fat_common::parse_dir_sector`, shared with `fat32.rs`) reconstructs the long name - checksum-verified against the short entry it describes - for both `ls` display AND direct lookup: `cat`/`rm`/a resize via `write_file` all work by *either* the real long name or the generated short alias, not just whichever one `ls` happens to show, since `find_entry_location_in` shares the identical reconstruction state machine (`LfnState`) with the display path. Originally shipped capped at a single 13-character long-name entry, then extended (same Fase arc, one iteration later) to `build_lfn_entries` chaining up to 15 of them - 195 characters - the largest that still keeps a new entry's required slots (long entries plus the one short entry) within its own deliberate single-sector limit (16 entries; the search simply continues into the next sector rather than splitting a slot run across both, and a bounds check added alongside the multi-chunk extension rejects any `count` over 16 outright rather than risk it silently computing a byte offset past a single sector buffer). **Two real bugs found and fixed by the single-chunk self-test, not by inspection**: a plain 8.3 name typed directly skipped all collision checking against an already-generated VFAT alias, so two directory entries could end up sharing one identical short name, corrupting whichever lookup found the wrong one first - fixed by checking `existing_short_names_in` on that path too, not only when an alias is freshly generated; and `read_file` and `delete_file`/`write_file` used two entirely separate matching paths that silently disagreed - reading found a VFAT file only by its long name, deleting only by its short alias - fixed by unifying `read_file` onto the same `find_entry_location_in` the others already used, now trying both names. Verified end-to-end at both boundaries: a 13-character single-chunk name with an embedded space (`ls` shows the real name, reading back succeeds by *both* the long name and the alias, a colliding plain-alias create is correctly rejected, delete and confirm gone by both names - repeated for a directory, deleted by its long name specifically to exercise both lookup directions) and, one iteration later, a 32-character name needing 3 chained long entries (created, shown, read back correctly by *both* names again - proving the multi-chunk reconstruction on the read side, general from the start but never previously exercised past one chunk, actually works - then deleted by its long name to exercise `find_entry_location_in`'s own multi-chunk accumulation specifically). All checks passed identically across 3 repeated boots each time, with zero regression across every other FAT12 self-test suite in the same boot log. |
| Multi-segment shell paths | **Real - `touch`/`cat`/`rm`/`mkdir`/`rmdir`/`ls` all understand `DIR1/DIR2/.../NAME` now, any number of levels deep, not just one.** `Fat12Info`'s own nested-subdirectory support (`DirLocation::Cluster`) has had no depth limit since it was first generalized - only `shell.rs`'s own path parsing did, hard-rejecting a second `/` and never splitting a path at all for `mkdir`/`rmdir`/`ls`. Replaced the old one-level `split_path` with `split_segments` (validates and splits every `/`-separated piece) and a new `resolve_dir_path` that walks an arbitrary list of directory names from the root to the innermost one's cluster, reusing the exact `list_root_directory`/`list_directory` calls already proven correct by every earlier FAT12 Fase. `mkdir`/`rmdir` reuse the same parent-chain-plus-final-component split file paths use (`mkdir A/B` creates `B` inside already-existing `A` - matching plain `mkdir`'s usual behavior, not `-p`: a missing parent segment is a real, honest error); `ls DIR1/DIR2` resolves the *whole* path to the directory being listed instead. This is the first time a person at the `AgentOS>` prompt can create, populate, and list a nested directory at all - Fase 36 proved nesting worked at the `Fat12Info` API level, but nothing before this exposed it interactively. Verified through the real `dispatch_command` path (not calling `Fat12Info` directly): `mkdir MULTIOUT` → `mkdir MULTIOUT/MULTIIN` (a directory created *inside* another one by name, from the shell, for the first time) → `touch`/`cat` a file two levels deep → `ls MULTIOUT/MULTIIN` shows its 3 entries → `rm` the file → a second `cat` correctly fails with **`"FAT12: file not found in directory"`** specifically, proof the path genuinely routed two levels down rather than coincidentally failing some other way → `rmdir MULTIOUT/MULTIIN` then `rmdir MULTIOUT` clean up. All nine steps correct on the first attempt, identical across 3 repeated boots, zero regression across every other FAT12/shell self-test in the same boot log. |
| VirtIO-net / TCP/IP stack | `net::virtio_net` (the TCP/IP-facing driver) is still simulated - fixed MAC, packet counters, no real VirtIO MMIO/virtqueues. **`net::e1000.rs` reaches the real NIC, and TX is now fully confirmed working end-to-end.** Finds the device via PCI (vendor `0x8086`/device `0x100e`, confirmed present at 00:03.0 by real enumeration), reads its real BAR0, and reads back real MMIO registers - no new page-table mapping code needed, since this kernel already identity-maps all physical memory at a fixed offset for the VGA text buffer, and that mechanism turned out to cover PCI MMIO space too. The MAC read from the real RAL0/RAH0 registers is `52:54:00:12:34:56` - QEMU's well-known default NIC MAC, now read for real off actual hardware. A real transmit descriptor ring is built (fresh physical frames via `memory::frame_allocator`, Fase 21), a real ARP request is written into it, the hardware dequeues it (`TDH` advances), and - as of Fase 44 - **the descriptor's Descriptor-Done status bit genuinely gets written back too**, confirmed by direct register read-back (`dd=true`), identically across 3 repeated boots. **A real, two-round mystery (Fase 22, Fase 32), resolved by investigating something else entirely**: every prior round correctly ruled out wrong register offsets, `TIPG`/`CTRL.SLU` misconfiguration, a starved poll loop, CPU cache incoherency, and deferred completion - each with its own real experiment, none of them the actual cause. The real answer surfaced while researching real RX support (see below): QEMU's `hw/pci/pci.c` only enables the memory region every `pci_dma_read`/`pci_dma_write` call routes through (`bus_master_enable_region`) once the guest sets the PCI Command register's Bus Master Enable bit - a real, standard PCI/PCIe requirement (a freshly enumerated device starts with bus mastering *disabled*, a genuine safety property), not a QEMU quirk. This kernel had simply never done it - `pci.rs` was read-only by design until Fase 44 added `write_config_word`/`PciDevice::enable_bus_mastering`. That single call, and nothing else, made `DD` start appearing: `TDH` is an internal register update (unaffected by bus mastering, hence always correct), while `DD` is a real DMA write to guest memory (silently dropped without it) - precisely the asymmetry both investigation rounds observed but couldn't explain from inside this driver's own, already-correct code. See `net/e1000.rs`'s module doc for the full two-round investigation and its resolution. **RX is now real too (Fase 45), and it genuinely received a real reply from the network on the very first attempt.** `receive_test_frame` arms a real receive descriptor ring (register offsets/`RCTL` bits/descriptor layout verified against QEMU's actual source, same discipline as the TX investigation) *before* triggering `send_test_frame`'s ARP request, then polls for a reply - and QEMU's SLIRP backend (the default user-mode network gateway at `10.0.2.2`) answered it: a genuine 64-byte Ethernet frame arrives, addressed to this kernel's own MAC, EtherType ARP. Verified as a real reply, not a same-shaped coincidence: the ARP `OPER` field is `0x0002` (reply, not request), the Sender Hardware Address matches the Ethernet source MAC (internal cross-consistency a malformed frame wouldn't have), and the Sender Protocol Address is `10.0.2.2` - *exactly* the IP the original request asked about. Identical, byte-for-byte, across 3 repeated boots. A new `netcheck` shell command (Fase 46) exposes this same TX+RX round trip interactively, on demand, rather than only ever at boot - zero changes to `net::e1000` itself, since `receive_test_frame` was already proven correct and is reused as-is. |
| IPv4 + ICMP protocol layer (`net::icmp`) | **Real header/checksum construction and parsing, deliberately not wired to the NIC yet.** `net::icmp` builds and parses real IPv4 headers (RFC 791) and ICMP echo request/reply messages (RFC 792), including the actual RFC 1071 Internet checksum algorithm - big-endian 16-bit word summation, carry-fold, one's-complement, with the odd-byte-padding edge case handled explicitly. Every format detail was checked against the real RFCs rather than relied on from memory, given how a wrong checksum fails silently: the receiving side just never replies, with no crash or error to point at the cause - a harder symptom to root-cause than the e1000 driver's own DD-bit mystery above. Pure byte-buffer logic, no hardware dependency at all - genuinely sending/receiving one over the wire needs a destination MAC address (ARP resolution, which doesn't exist yet) and would touch the e1000 TX/RX paths that are now proven correct and CI-asserted across three Fases; proving these primitives correct in isolation first, before anything depends on them, follows the same order the frame allocator and VFAT entry-building both used. **A real bug surfaced and got fixed during this Fase's own verification, not by chance**: the checksum-verification check initially compared a re-summed, already-checksummed buffer against `0xFFFF` - correct per RFC 1071's own wording, but only when read as "the sum *before* the final one's-complement step". This code's `internet_checksum` function returns that complement directly (`!sum`, the value meant to be *embedded* in a checksum field), so re-running it over a validly-checksummed buffer actually returns `!0xFFFF = 0x0000`, not `0xFFFF` - every genuinely valid buffer was being silently rejected. A pure round-trip test (build a message, then check it with the same function) would never have caught this, since both sides would have agreed with each other while disagreeing with any real peer computing the checksum independently - it was only caught because the self-test also included two independent, hand-computed checksum vectors verified by manual arithmetic before ever running the code. Fixed with a dedicated `checksum_is_valid` helper that encapsulates the correct constant in one place, rather than leaving every call site to compare against the right value itself. Verified: the two hand-computed vectors (one exercising the even-length case, one the odd-byte-padding case) match by hand; a full request/reply built via `build_icmp_echo` (odd-length end to end, so the integration path exercises the same padding logic too) round-trips through `parse_icmp_echo` correctly; a deliberately corrupted reply (one payload byte XOR-flipped) is correctly rejected; and a freshly-built IPv4 header's own checksum verifies too - all six checks passing identically across 3 repeated boots, zero regression across the entire prior self-test suite in the same boot log. |

## Building & running the kernel

Requires the **nightly** Rust toolchain (pinned per-directory via `rust-toolchain.toml`) and [QEMU](https://www.qemu.org/).

```bash
# 1. Build the kernel itself
cd agentos-kernel
cargo build --release

# 2. Package it into a bootable disk image (separate crate, host target)
cd ../kernel-runner
cargo build --release
./target/release/kernel-runner "../agentos-kernel/target/x86_64-unknown-none/release/agentos-kernel" "../agentos-kernel/target/disk-image"

# 3. Boot it
qemu-system-x86_64 -drive format=raw,file=../agentos-kernel/target/disk-image/agentos-bios.img
```

Or just run [`agentos-kernel/boot_kernel.bat`](agentos-kernel/boot_kernel.bat), which automates all three steps and opens an interactive QEMU window.

For a headless run with serial output captured to your terminal instead:

```bash
qemu-system-x86_64 -drive format=raw,file=agentos-kernel/target/disk-image/agentos-bios.img -serial stdio -display none -no-reboot -no-shutdown
```

## Running the TypeScript dashboard simulator

```bash
npm install
npm run build
npm start
```

Serves the mocked dashboard UI in `public/` against the in-memory "kernel" in `src/server/kernel.ts`. Nothing here talks to real hardware or a real model.
