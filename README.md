# AgentOS

[![kernel-ci](https://github.com/charlessonamericantrading/iaos/actions/workflows/kernel-ci.yml/badge.svg)](https://github.com/charlessonamericantrading/iaos/actions/workflows/kernel-ci.yml)

An "AI-native" operating system project, explored in two independent, **not yet integrated** directions:

1. **[`agentos-kernel/`](agentos-kernel/)** — a real bare-metal kernel written in Rust (`#![no_std]`), booting on actual x86_64 hardware/QEMU. This is the actively developed half of the project.
2. **[`src/`](src/) + [`public/`](public/)** — a TypeScript/Express dashboard that simulates what an AI-agent OS's control plane might look like (scheduler, memory, sandbox). It is a UI mock: no real model calls, no persistence, everything in-memory. Parked in favor of the kernel.

There is no bridge between the two yet — `src/bridge.ts` only POSTs one canned sample event to demonstrate the shape of an API, it does not talk to the kernel.

## Current status (honest version)

The kernel **boots for real** in QEMU via the [`bootloader`](https://github.com/rust-osdev/bootloader) crate and reaches an interactive prompt. What's actually real hardware/software vs. simulated scaffolding, as of this commit:

| Subsystem | Status |
|---|---|
| Boot (`bootloader` crate, BIOS) | **Real.** Verified boot to `AgentOS>` prompt. |
| GDT / IDT / CPU exceptions | **Real.** breakpoint, double-fault (own IST stack), page-fault, GPF, divide-error, invalid-opcode all wired and verified via a live `int3` self-test. |
| 8259 PIC + hardware interrupts | **Real.** PIC remapped to vectors 32-47 (avoids colliding with CPU exception vectors 8-15), interrupts enabled, timer (IRQ0) and keyboard (IRQ1) are interrupt-driven, not polled. |
| Physical memory / paging / heap | **Real.** Frame allocator walks the actual `BootInfo` memory map (skips regions already used by the kernel/bootloader); the heap is properly mapped page-by-page before use. `alloc` (`Vec`, `Box`, `String`) works. 1 MiB heap (raised from an initial 100 KiB after `cat`-ing a real file proved that too small - see FAT12 row below). The same frame allocator instance is now also reachable *after* boot's initial heap setup via a global `memory::frame_allocator::allocate_frame()` - a prerequisite for any future code needing dedicated physical memory outside the heap (a real e1000 TX/RX descriptor ring being the motivating case - see NIC row below). Deliberately the *same* allocator, not a fresh one built later from the same memory map: a fresh one would start handing out frame 0 again, which the heap already owns by then. Verified by allocating 3 frames after boot and write/read-back-testing a pattern through each (via the same `PHYS_MEM_OFFSET` mechanism the VGA buffer and e1000 probe use) - came back distinct and exactly 4 KiB apart (`0x163000`, `0x164000`, `0x165000` locally), proving these are genuine, usable, non-overlapping memory, not just plausible numbers. |
| Agent scheduler (`ps`-visible) | **Now really unified with both the cooperative and preemptive schedulers** (next two rows): `spawn_cooperative` and `run_preemptive_demo` both register real PCB entries via `SCHEDULER.lock().spawn(...)`, and each scheduler keeps its entries' `state`/`stack_pointer` honest as tasks actually run, yield/get switched, and finish - `ps` genuinely reflects live scheduler state now, not just a fixed table. Still partial for one thing: the 4 processes spawned directly at boot as a self-test (`kernel-supervisord` etc.) have PCB entries but no real stack/registers behind them - nothing ever actually schedules them as tasks. |
| Cooperative task scheduler | Real, and now **PCB-unified** (previous row). `scheduler/context_switch.rs`'s `#[unsafe(naked)]` `switch_to` swaps RSP + the 6 callee-saved registers between stacks (xv6-style) - `spawn_cooperative`/`yield_now`/`finish_current_task` build a priority-ordered N-task cooperative scheduler (up to 4 tasks) on top of it, and each task is now a real `ps`-visible process, not just an internal one. Verified two ways in QEMU: `ps` dispatched from *inside* a running task shows it `RUNNING` with a real (nonzero, heap-range) stack pointer while its not-yet-scheduled siblings still show `READY` with no stack pointer recorded yet; `ps` again after the demo shows all three `DEAD` (terminated) with distinct real stack pointers exactly `TASK_STACK_SIZE` (16 KiB) apart, matching their actual heap layout - strong evidence these are genuine addresses, not placeholders. A task only ever changes on its own voluntary `yield_now` call. |
| **Preemptive scheduler (real)** | Real, and now **PCB-unified too**. `scheduler/preemptive.rs` hooks the same `switch_to` primitive into the timer IRQ (`interrupts.rs`) so tasks that *never* call `yield_now` at all still get forced off the CPU - proven with two infinite, non-cooperating loops that both end up with large, nonzero counters after a timed window, which is only possible if the timer genuinely reclaimed the CPU from each without asking. Two real, subtle bugs surfaced and got fixed getting here, both the same root cause: state shared between an interrupt handler and normal code needs `AtomicBool`/`AtomicU64`, not a plain `static mut` - in a release+LTO build, the compiler hoisted a `while flag { hlt() }` poll loop's read out entirely (an infinite hang, since it never noticed the interrupt handler had cleared the flag), and separately treated a counter only ever incremented inside an infinite loop with no in-function reader as having no provable side effect. Neither was caught by clippy or by reasoning about the design alone - only by actually booting it and getting a genuinely wrong/hung result, then diagnosing why. **PCB unification needed real interrupt-safety care**, unlike the cooperative case: `tick()` runs inside the timer interrupt handler, so it uses `SCHEDULER.try_lock()`, never the blocking `.lock()` - taking a normal lock there would deadlock permanently on this single core if the timer ever fired while normal code held it mid-update, since that code could never resume to release it until this very handler returns. A skipped update (vanishingly rare, and harmless - `ps` is diagnostic-only) self-corrects the next tick, ~55ms later. Verified the same two ways as the cooperative case, plus 3 repeated full boots to check for interrupt-timing-dependent flakiness specifically (none observed - identical serial output every run). |
| Context switch primitive (hand-written asm) | **Still flagged for human review** - not yet reviewed as of this note; built further on it anyway per the project owner's explicit instruction not to wait. Both schedulers above share it. |
| Interactive shell | Real (small). The `AgentOS>` prompt is IRQ1-driven (not polled), buffers a real line (heap-backed `String`) with backspace, Left/Right cursor movement, Shift (uppercase letters plus `~`/`-`/`_`), and Up/Down command history (a real `Vec<String>`), and dispatches `help` / `ps` / `mem` / `uptime` / `date` / `lspci` / `disk` / `ls` / `cat` / `touch` / `rm` / `clear` against the live scheduler, KV-cache, heap, timer-tick, real-time-clock, and real disk/filesystem state - not canned output. Insert/backspace both act at the cursor, not just at the end of the line - typing "hep", pressing Left once, then typing "l" correctly produces "help", not "hepl" or "lhep". Verified in QEMU: that exact sequence dispatches the real `help` command (its actual output appears in the log), not an "Unknown command" line. **Shift was a real, practical gap, not a nice-to-have**: before it, a real person at the keyboard could never actually type `cat KERNEL~1` themselves - no way to produce an uppercase letter or `~` at all - even though self-tests could dispatch it directly. Verified by feeding a realistic scancode sequence holding Left Shift across "KERNEL~" (letters plus the backtick key, which shifts to `~`) and releasing it before the unshifted "1": dispatches the real `cat` command a second time in the log (identical byte count to the direct self-test), not an "Unknown command". **`touch`/`rm` close a similar gap for file writes**: `Fat12Info::create_file`/`delete_file` (see the FAT12 rows below) existed for several Fases but were only ever reachable from hardcoded `main.rs` self-tests - a real person at the prompt had no way to create or delete a file themselves. `touch FILENAME [content...]` joins whatever's left on the line (single-spaced - this shell has no quoting, so exact original spacing isn't preserved) and creates a new file with it as content; `rm FILENAME` deletes one. Both are FAT12-only, matching `create_file`/`delete_file` themselves - a real FAT32 disk would get a clear "not implemented yet" error rather than a silent no-op, currently untested in practice since this disk is FAT12. Verified in QEMU through the *actual* `dispatch_command` parsing path (not by calling `Fat12Info` methods directly, unlike the tests that first proved `create_file`/`delete_file` themselves correct): `touch SHELLNEW.TXT hello from the real shell` creates a real 25-byte file, `cat` reads the exact same content back (first 4 bytes `68 65 6c 6c` - "hell", confirming genuine content, not just a matching length), `rm` deletes it, and a second `cat` then fails with "file not found" - identical across 3 repeated boots. |
| KV-cache memory manager | Real (small). Each block is a genuine heap allocation (`Box<[u8]>`, 4 KiB - sized for the current 1 MiB demo heap, not a realistic model-serving size yet); freeing a block really deallocates it. Previously used a fabricated address (`0x2000000 + idx*size`) that nothing was ever mapped to. |
| GGUF model loader / tensor engine | Simulated. Parses a hardcoded 24-byte sample header and runs a toy 4x4 matmul+ReLU; does not load or run a real model file. |
| PCI bus enumeration | Real. `pci.rs` reads real config space via the legacy `CONFIG_ADDRESS`/`CONFIG_DATA` I/O ports (read-only - never reconfigures anything) and the `lspci` shell command lists what it finds. Verified against known-good hardware IDs, not just "didn't crash": QEMU's default machine reports exactly the expected i440FX host bridge (`8086:1237`), PIIX3/4 ISA/IDE/ACPI bridges (`8086:7000`/`7010`/`7113`), standard VGA (`1234:1111`), and an e1000 NIC (`8086:100e`) - all real, recognizable vendor:device IDs, not fabricated ones. Only scans bus 0 (no bridge recursion yet). |
| Real-time clock (CMOS RTC) | Real. `rtc.rs` reads the actual wall-clock date/time via the legacy CMOS I/O ports (0x70 index/0x71 data) - the `date` shell command shows it. Waits out the chip's Update-In-Progress flag first (a real, if uncommon, torn-read hazard if ignored) and checks Status Register B rather than assuming BCD vs. binary or 12h vs. 24h mode, since real hardware (and QEMU's emulation) can be configured either way. Verified about as concretely as a "real" check can be: QEMU syncs this clock to the host's actual wall-clock time by default, and the value read back during local testing matched the real date/time at the moment of the test, to the second. No century register exists reliably, so the year assumes 20xx. |
| Disk I/O (ATA PIO) | **Real, both read and write.** `ata.rs` reads/writes real 512-byte sectors on the primary ATA master via classic PIO (ports 0x1F0-0x1F7) - the `disk` shell command reads LBA 0 and checks for the `0x55AA` MBR boot signature, which is genuinely present since it's reading our own disk image. **Caught a real bug getting the read side working**: the drive raises IRQ14 on command completion regardless of whether anything is waiting on it, and this kernel had no handler for that vector at all - the first real read double-faulted the instant interrupts came back on after the operation. Fixed with a real (if minimal) `ata_primary_interrupt_handler` in `interrupts.rs`, not just by suppressing the symptom - and that same fix is why `write_sector` (added later, prerequisite for any future FAT write support) worked cleanly on the first real boot test, no repeat of that bug. `write_sector` follows the same PIO handshake as reads (select drive/LBA, wait for `DRQ`, transfer 256 words) plus a `CACHE FLUSH` (`0xE7`) afterward so a caller getting `Ok` back knows the write is genuinely committed, not just buffered. Verified with a real write-then-read-back test at a sector safely inside the FAT12 partition's unused tail, confirmed byte-for-byte identical across 3 repeated boots. |
| Partition table (MBR) | Real. `partition.rs` parses the 4 primary partition entries out of the boot sector already read via ATA. On our own disk image this finds two real bootable entries: a small internal region (the `bootloader` crate's own boot stages) and a partition typed `0x0C` ("FAT32 LBA") - **which turned out to actually be formatted FAT12**, see below. |
| FAT32 / FAT12 filesystem | **Real - read (`ls`/`cat`), overwrite-existing-file write, and now genuine new-file creation too, all verified end-to-end.** `fat32.rs` parses the BPB and can walk cluster chains / list a directory / read a file by name - **but our own disk's `0x0C`-typed partition is actually FAT12**, confirmed by reading the raw boot sector (`root_entry_count=512`, and the on-disk filesystem-type string literally reads `"FAT12   "`, volume label `"agentos-ker"`) - the `mbrman`/`fatfs` tooling that builds our disk image apparently doesn't always match the MBR type byte to the filesystem it actually formats for a volume this small. `shell.rs` tries FAT32 first and falls back to `fat12.rs` (packed 12-bit FAT entries, two per 3 bytes; fixed-location root directory instead of a cluster chain) when it doesn't apply - which is what makes both commands actually work on this disk. `ls` lists all 3 real files present (`BOOT-S~1`, `BOOT-S~2`, `KERNEL~1` - the `bootloader` crate's own two stages plus our kernel binary; each roughly 116-150 KiB, exact byte counts not pinned anywhere since they turned out to shift a little between build machines - see next paragraph). `cat KERNEL~1` reads the whole file back through a real cluster-chain walk (its length matching whatever `ls` reported that boot), and the first 4 bytes are always `7f 45 4c 46` - the genuine ELF magic number (`\x7fELF`), a build-independent invariant and about as strong a correctness proof as available without a full checksum. **Found the hard way (three times)**: first, the initial FAT32 code silently misread FAT12's differently-shaped BPB as FAT32 fields, computing a garbage LBA in the billions; fixed by checking `root_entry_count` (FAT32 always zeros it, FAT12/16 never do - the standard, authoritative discriminator) and failing with a clear, honest message instead of guessing. Second, actually `cat`-ing a real file panicked with a heap-allocation failure - every real file on this disk (116-148 KiB) turned out to be bigger than the entire 100 KiB heap that existed at the time, since `read_file` needs one contiguous allocation for the whole file; fixed by raising the heap to 1 MiB (see memory row above). Third, a CI regression check that hardcoded the exact byte count seen locally (`KERNEL~1 132992 bytes`) promptly failed on the Linux CI runner, which built a `KERNEL~1` of 132960 bytes from the identical source - the kernel ELF's own size isn't stable across build machines, so the CI check was rewritten to assert on the build-independent ELF magic bytes instead of a specific length. Directory-entry parsing (32-byte short-name entries, VFAT long-name entries recognized and skipped) is shared between both filesystem modules via `fat_common.rs`. **Fourth thing found the hard way**: `fat12::write_file` (new - overwrites an existing file's content at the same byte length only, reusing its existing cluster chain; no directory/FAT changes, so creating a new file or resizing one are still separate, unimplemented, substantially bigger features) was first tested by overwriting `BOOT-S~2` with a throwaway pattern, on the assumption that nothing in this kernel's own self-tests reads it so it was "safe." Wrong assumption, caught by a routine repeat-boot-test: `BOOT-S~1`/`BOOT-S~2` are the `bootloader` crate's own boot-stage *executables*, run by the BIOS before this kernel exists - QEMU's `-drive` writes straight through to the host `.img` file, so leaving that overwrite in place corrupted the boot chain for every subsequent boot against the same image (the first boot looked fine, since its own chain had already handed off to this kernel before the corruption happened; only the *next* boot attempt hit a totally empty serial log, no panic, because a corrupted stage 2 never got far enough to run any kernel code at all). Fixed by having the self-test unconditionally restore the original content afterward - confirmed safe across 3 repeated boots against the same unregenerated image. |
| FAT12 new-file creation | **Real - genuinely new files, not just overwriting existing ones - and now of any size, not just single-cluster.** `Fat12Info::create_file` finds as many free clusters as the data needs (`find_free_clusters`, one pass over the in-memory FAT collecting distinct `0x000` entries - calling a "find one free cluster" function repeatedly would just return the same cluster every time, since nothing marks one "taken" until its FAT entry is actually written) and a free root-directory slot (first byte `0x00`/`0xE5`), writes the data across all of them, chains each cluster to the next in the FAT (last one marked end-of-chain), and writes a real short-name (8.3) directory entry - including a genuine creation timestamp read from the CMOS RTC (Fase 20), not a zeroed placeholder. Short names only still (no VFAT long-name entries). Writing a 12-bit FAT entry correctly handles the one real edge case that format has: at specific cluster numbers (341, 682, 1023...) the packed entry straddles a 512-byte sector boundary, so both sectors are read/written when that happens rather than assumed never to occur. Verified in QEMU: creates `AGENTOS.TXT`, reads it back and confirms the content matches, and `ls` genuinely shows the entry count going from 3 to 4. Repeat boots against the same unregenerated image correctly detect the file already exists (no duplicate entry, no double-allocated cluster) and still read back the same real content - confirmed identical across 3 repeated boots, learning directly from the FAT12-write lesson above about what "safe to run every boot" actually requires. **Multi-cluster support (originally deferred - "several free-cluster lookups tracked against each other so the same free cluster is never handed out twice" was real, meaningfully more bookkeeping) verified separately**: creates a 3100-byte file (this disk's clusters are 1024 bytes each, so this genuinely needs 4 chained clusters, not 1), reads it back byte-for-byte against a deterministic pattern (not just a matching length), and deletes it - which also happens to be the first real test of `delete_file`'s cluster-chain walk against an actual multi-cluster chain (Fase 27 only ever proved that logic against single-cluster files, though it was written generally from the start). All correct, identical across 3 repeated boots. |
| FAT12 file deletion | **Real - frees both the cluster chain and the directory slot, not just a cosmetic marker.** `Fat12Info::delete_file` finds the entry's exact on-disk location (`find_entry_location`, which tracks slot index unlike `list_root_directory`), walks its full cluster chain zeroing each FAT entry back to `0x000`, and marks the directory entry's first byte `0xE5` (the standard FAT convention `find_free_root_entry` already knew to treat as reusable). **Found the hard way, a genuine cache-coherence bug**: the very first test run failed with `cluster chain hit a free (0) entry unexpectedly`, even though the file had been created moments earlier in that same boot. Root cause: `write_fat_entry_to_disk` (used by both `create_file` and `delete_file`) wrote the new FAT value straight to disk but never updated the in-memory `fat_bytes` copy loaded once at mount time - so any later call within the same `Fat12Info` that consulted the cache (`next_cluster`, `find_free_cluster`) saw stale, pre-write data. This had been silently latent since `create_file` was added: `read_file` never surfaced it because its read loop returns as soon as it has enough bytes, so a single-cluster file never reaches its own `next_cluster` call - `delete_file` is the first caller that walks the chain unconditionally, regardless of file size, which is exactly why it's the one that exposed a bug that had been sitting there since the previous Fase. Fixed by having `write_fat_entry_to_disk` write the same two bytes into `fat_bytes` right after the disk write succeeds, keeping the cache coherent for the rest of that mount's lifetime. Verified in QEMU: creates a dedicated `DELETEME.TXT` (kept separate from the already-verified `AGENTOS.TXT`), confirms it exists, deletes it, then confirms `read_file` now fails and `ls`'s entry count drops back down - correct across 3 repeated boots against the same unregenerated image, including boots where the file first had to be freshly re-created (since the previous boot's delete had already removed it from disk). |
| VirtIO-net / TCP/IP stack | `net::virtio_net` (the TCP/IP-facing driver) is still simulated - fixed MAC, packet counters, no real VirtIO MMIO/virtqueues. **`net::e1000.rs` reaches the real NIC**: finds it via PCI (vendor `0x8086`/device `0x100e`, confirmed present at 00:03.0 by real enumeration), reads its real BAR0, and reads back real MMIO registers - no new page-table mapping code needed, since this kernel already identity-maps all physical memory at a fixed offset for the VGA text buffer (`vga_buffer.rs`), and that mechanism turned out to cover PCI MMIO space too (confirmed by booting, not assumed). The MAC read from the real RAL0/RAH0 registers is `52:54:00:12:34:56` - QEMU's well-known default NIC MAC (the *exact* value this project's own `virtio_net.rs` had been using as a hardcoded placeholder, coincidentally - now read for real off actual hardware instead of typed in as a guess). BAR0's *exact* address is NOT a similarly stable fact: it read `0xfebc0000` locally but `0xfeb80000` on the CI runner's different QEMU version, from the identical source - SeaBIOS's PCI resource assignment isn't pinned the way the device's own emulated register contents are. **TX is real but genuinely incomplete, reported honestly rather than papered over**: a real transmit descriptor ring is built (fresh physical frames via `memory::frame_allocator`, Fase 21), a real ARP request is written into it, and the hardware provably dequeues it - `TDH` advances from 0 to 1 the instant `TDT` is written, confirmed by direct register read-back. What doesn't happen: the descriptor's Descriptor-Done status bit never gets written back, in every variant tested (register offsets and layout cross-checked against QEMU's own source and a real shipped driver; `TCTL`/`TIPG` correctly set; ruled out a tight-poll-loop starving QEMU's event loop by halting for ~11 real seconds between checks; `CTRL.SLU` already set by default; tried both an experimental EtherType and a fully valid ARP request with identical results). Root cause unresolved as of this note - see `net/e1000.rs`'s module doc for the full investigation. No RX attempted yet either. |
| Syscall dispatcher | Minimal. A handful of syscall numbers wired to stub handlers. |

Nothing above is faked to look more finished than it is — this table is meant to stay accurate as the project grows, not to be a wishlist.

## Building & running the kernel

Requires the **nightly** Rust toolchain (pinned per-directory via `rust-toolchain.toml`) and [QEMU](https://www.qemu.org/).

```bash
# 1. Build the kernel itself
cd agentos-kernel
cargo build --release

# 2. Package it into a bootable disk image (separate crate, host target)
cd ../kernel-runner
cargo build --release
./target/release/kernel-runner "../agentos-kernel/target/x86_64-unknown-none/release/agentos-kernel" "../agentos-kernel/target/disk-image"

# 3. Boot it
qemu-system-x86_64 -drive format=raw,file=../agentos-kernel/target/disk-image/agentos-bios.img
```

Or just run [`agentos-kernel/boot_kernel.bat`](agentos-kernel/boot_kernel.bat), which automates all three steps and opens an interactive QEMU window.

For a headless run with serial output captured to your terminal instead:

```bash
qemu-system-x86_64 -drive format=raw,file=agentos-kernel/target/disk-image/agentos-bios.img -serial stdio -display none -no-reboot -no-shutdown
```

## Running the TypeScript dashboard simulator

```bash
npm install
npm run build
npm start
```

Serves the mocked dashboard UI in `public/` against the in-memory "kernel" in `src/server/kernel.ts`. Nothing here talks to real hardware or a real model.

## Repository layout

```
agentos-kernel/   Rust #![no_std] kernel - GDT/IDT, paging/heap, scheduler, syscalls, drivers
kernel-runner/    Host-target helper crate that packages the kernel ELF into a bootable disk image
src/, public/     TypeScript/Express dashboard simulator (parked, not integrated with the kernel)
```
